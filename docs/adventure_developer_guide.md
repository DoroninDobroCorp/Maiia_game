# SUR: разработка приключений и живого архива

Практическое дополнение к [спецификации](MISSION_GAMIFICATION_AND_LIVING_ARCHIVE_SPEC.md), [контракту контента](../content/CONTRACT.md) и [семейной инструкции](adventure_family_guide.md). Ниже описана текущая реализация; ограничения экспортированной сборки выделены отдельно.

Редактор доступен из «Новая глава»; экспорт черновиков остаётся в «Редактор Phase C» прежней консоли.

**Тексты для ребёнка.** Определения квестов замораживаются в снимке экземпляра, поэтому правка JSON не доходит до уже начатых прохождений. Формулировки, которые должны сразу работать у всех сохранений, лежат в `mission_guide.gd`: рассказ героя и цель миссии, название и задача каждого шага, реплика персонажа до шага и после него, пошаговые инструкции, подписи полей, список «Понадобится», детские варианты чек-листов. Всё, чего нет в гиде, берётся из исходного JSON, поэтому семейные и импортированные истории не затрагиваются. Чек-листы хранятся по позиции, а не по тексту: замена применяется только при совпадении количества пунктов (это проверяет `test_mission_guide.gd`). Чтобы новая миссия получила экран «Миссия», добавьте её записи в `MISSIONS` и `STEPS`.

## Четыре уровня расширения

### 1. Новая миссия из известных действий

Возьмите полный пакет [AR02 «Три силуэта»](../content/examples/three_silhouettes.schema2.json). В редакторе это «Копия: три силуэта». Измените `quest_id`, название, критерии, этапы и содержимое действий; используйте существующие типы, рецепты и выдачи. Для нового задания — новая пара `quest_id/revision`; для изменения опубликованного — `ContentLibraryService.next_free_revision(state, quest_id)`.

Пакет содержит `schema_version: 2`, `package_type: "sur_quest_pack"`, `package_id`, `required_capabilities` и `quests`. Сама миссия тоже имеет `schema_version: 2` и положительную целую `revision`. Не путайте версии контента 1/2 со схемой сохранения `1.3.0`.

В `quest.adventure` хранится полный снимок: `stages`, `interactions`, `dialogues`, `work_recipes`, `grant_definitions`, при необходимости `lexicon`, `channels`, `envelopes`, `final_check`. Поля этапа: `stage_id`, `title`, `summary`, `criteria`, `prerequisite_stage_ids`, `completion_policy`, `budget_share`, `grant_ids`, `atlas_unlock_ids`, `work_recipe_id`, `interaction_ids`, `next_hint`. `interactions` — словарь по ID, совпадающим с `interaction_id` внутри записи. Точные вложенные конфигурации восьми действий приведены в [CONTRACT.md](../content/CONTRACT.md).

Путь публикации: сохранить DRAFT → `validate_quest()` → предпросмотр → `QuestService.approve_and_publish()`. Импорт всего пакета через `import_package()`/`import_package_json()` атомарно создаёт DRAFT; разрешений не переносит. `build_export_package()` исключает одобрения. Само чтение JSON ничего не публикует.

Для импортируемой миссии менять `AppRoot` не требуется. Для новой встроенной добавьте файл в `content/quests/` и путь в `AdventureContent.QUEST_FILES`; при включении в главу обновите её определение. Текущий генератор `content/tools/build_first_chapter.py` пересоздаёт именованные JSON: меняйте источник генерации согласованно и проверяйте diff. Выпущенную ревизию не переписывайте.

Каталог сохраняет исходные 11 заданий, банк из 24 и три приключения FG01/FG11/FG08 ревизии 2: всего 38 встроенных определений. Исторические ревизии не удаляются. Защита встроенных определений проверяет все ревизии, включая скрытые более новой. Принятый `QuestInstance.quest_snapshot` и его `content_hash` остаются источником истины даже после публикации следующей версии.

### 2. Новый рецепт экспоната или рамка

Если достаточно готовой рамки/альбома/терминала, используйте известный рецепт в данных. Для нового ID рецепта обновите `AdventureContent.WORK_RECIPE_IDS`, добавьте определение в замороженный `adventure.work_recipes` и соответствие вида работы в `CollectionService.RECIPES`. Если этап выдаёт новый предмет, нужны также `GRANT_IDS` и запись `grant_definitions`. Встроенные описания находятся в `content/exhibits/first_chapter_recipes.json`, но экземпляр должен содержать собственную копию зависимостей.

Особый способ показа требует реализации в `collection_browser.gd`/`gallery_room.gd`; одной строки в списке разрешений недостаточно. При необходимости обновите совместимость видов в `CollectionService.list_slots()`. Варианты рамок выбираются через UI и сохраняются как `room.frame_style`; новая картинка рамки требует ресурса и обработчика отображения. Не переименовывайте старые ID: старые выставки ссылаются на них.

Работа, её версия, экспонат и размещение — разные записи. Создавайте версии через `add_version()`, файлы — через `ArtifactService`, размещения — через `place_exhibit()`. Размещение хранит конкретный `version_id`; новая версия работы не обновляет его автоматически. Не копируйте медиа при каждом показе и не начисляйте XP за расстановку. Проверьте старую/новую версию, отсутствие файла, совместимость места и восстановление снимка зала.

### 3. Новый зал или пространственный шаблон

Ещё один экземпляр существующей галереи создаётся в UI или `CollectionService.create_room()`: новый код не нужен. Базовый шаблон `gallery_v1` имеет 12 стабильных мест; `station_favorites` — три отдельных места станции. Темы: `warm`, `dusk`, `daylight`. Дополнительный зал открывается после финала основной истории либо восьми разных личных работ.

Удалённые ID зарезервированы в `collections.retired_room_ids`; старые снимки также резервируют свои `room_id`. Не выдавайте их новым комнатам и не создавайте удалённый первый зал при `ensure_gallery()`. Восстановление без назначения `room_id` возвращает исходный зал; с назначением — применяет снимок к явно выбранному совместимому залу. Постоянное `station_favorites` не удаляется, его размещения снимаются отдельно. Если физических залов нет, контроллер открывает управление снимками.

`CollectionBrowser.navigation_context()` возвращает текущие работу, версию, зал, место и вкладку. Перед повторным `setup()` после успешной команды контроллер обновляет этот контекст: исходные параметры открытия экрана могут уже не совпадать с тем, что выбрал пользователь. Поиск UI использует `CollectionService.list_works()` и сохранённые названия историй/заметки версий без загрузки медиа.

Новая **геометрия** требует кода: сейчас нет загрузчика `content/room_templates/*.json`. Добавьте сцену/представление, новый `template_id` и набор мест в `list_slots()`, поддержку создания/выбора шаблона в сервисе и маршрутизацию в `AdventureController.open_gallery()`. Текущий контроллер загружает `scenes/world/gallery_room.tscn`. Стабильность `slot_id` нужна снимкам и размещениям; при изменении старого шаблона предусмотрите явную миграцию. Проверьте две комнаты с общей работой, удаление с сохранением снимка и переключение без изменения архива.

### 4. Новый тип взаимодействия

Добавьте ID в `AdventureContent.INTERACTION_TYPES`, строгую схему config и ссылок в `ContentValidation._validate_interaction()`, чистую проверку ответа в `AdventureRules.check_interaction()` и представление в `AdventureEpisode`. Если тип требует новых данных результата, согласуйте их с `AdventureService.record_attempt()` и проверкой завершения в `ActivityCommitService`; затем добавьте пример и проверки успешного, ошибочного и повторного ответа, помощи, черновика и повторной загрузки.

JSON не может назначать скрипт, команду, URL, путь приложения или произвольный callback. Для новой обязательной возможности объявите и реализуйте capability, затем добавьте её в `CAPABILITY_IDS`. Для новой точки атласа согласованно обновите `ContentValidation.ATLAS_IDS`, `AtlasService` и отображение карты. Расширение реестра означает поддержку поведения, а не обход валидатора.

## Строгая проверка данных

`validate_quest()` и `validate_package()` возвращают `{valid, errors}`; сервисные операции обычно возвращают `{ok, reason, ...}`. Показывайте ошибки автору до публикации.

| Ограничение | Текущее значение |
| --- | --- |
| Миссии в пакете | 1–50 |
| Этапы в миссии | 1–64; граф без циклов, все этапы достижимы |
| Диалоги | До 256 узлов суммарно на миссию, включая встроенные scripted_dialogue |
| Лексемы | До 1000 на миссию и суммарно в пакете |
| Текст и вложенность | Строка до 1200 символов; вложенность до 32 |
| Строковый импорт пакета | До 8 МиБ UTF-8 в `import_package_json()`; словарный API и вставка JSON в редакторе не имеют этого байтового барьера |
| Бюджет | Сумма обязательных `budget_share` равна `activity_budget`; необязательные этапы имеют 0 |
| Основные цели | FG01 — 40, FG11 — 60, FG08 — 40 XP; у поставляемых ревизий по шесть этапов |

Политики завершения: `automatic`, `self_attest`, `joint_review`. Проверяются вложенные типы, уникальные ID, ссылки на этапы/действия/диалоги/лексемы/рецепты/выдачи/атлас, известные навыки и эффекты. Разрешённые interaction/capability/grant/recipe ID берутся из `AdventureContent`. Произвольные пути, исполняемые поля и чужие одобрения отклоняются. Схема 1 сохраняет совместимость числовых `goal_steps`, например `[25, 50, 75, 100]`; в схеме 2 массивы текстовых шагов остаются строковыми.

FG01 хранит 100 стабильных лексем, а не 100 встретившихся словоформ: 20 конвертов вводят по пять, повторение ссылается на те же ID. Итог опирается на записанную попытку смешанной проверки; косметический выбор не засчитывает применение слова. Посещения FG08 и функциональные этапы FG11 требуют совместной проверки. Запуск готовой основы не доказывает ни прохождения, ни авторства.

## Сохранение, транзакции и миграция

`SaveService` поддерживает ровно `1.0.0`, `1.1.0`, `1.2.0`, `1.3.0`. Новые необязательные разделы исходного состояния:

```json
{
  "adventures": {"progress": {}, "grants": {}, "reward_lineages": {}, "pending_presentations": {}},
  "collections": {"works": {}, "exhibits": {}, "rooms": {}, "placements": {}, "snapshots": {}}
}
```

SaveService не подгружает AdventureService. После `load_game()` контроллер проверяет `read_only`, затем вызывает `ensure_adventures()`, `migrate_legacy()` и `ensure_collections()`. Старые разделы, история XP, ритуал, публикации и замороженные экземпляры сохраняются. Перед первой миграцией исходные байты копируются в `SAVE_PATH + ".premigration-original.json"`; этот файл не вращается вместе с тремя обычными резервными копиями и не заменяется сбросом.

Неизвестная схема возвращается как исходное состояние с `read_only: true` и `recovery_notice`. Нельзя подменять её default-state, запускать миграции или разрешать мутации. `save_game()` сам блокирует запись после такой загрузки, даже если вызывающий убрал флаг; также проверяет актуальную схему файла на диске. Для интерфейса доступны `is_write_blocked()` и `get_last_error()` с `{ok:false, reason, message}`.

Обычная мутация: глубокая копия состояния → сервис → `Save.save_game(candidate)` → заменить live-state только при успехе. `save_game()` возвращает bool; пишет и проверяет временный файл, копирует резервные файлы и атомарно заменяет основной без предварительного удаления. Ошибка сохраняет последний подтверждённый основной файл. Не выдавайте успех/реакцию мира до успешной записи.

Завершение этапа и совместный просмотр проходят через `ActivityCommitService.commit_stage()`/`review_stage()`: XP, grant, работа, атлас и отложенная презентация записываются вместе. `reward_lineage_id` и канонический ID результата предотвращают повторную награду при переоткрытии и миграции. `pending_presentations()`/`acknowledge_presentation()` позволяют показать реакцию после загрузки без повторной выдачи.

`AdventureService.migrate_instance(state, instance_id, revision, stage_mapping, actor_id)` переносит только явно подтверждённые действия. Значение mapping — ID завершённого старого этапа либо `{source_activity_id, note}` для подтверждённой старой активности; ключ — новый `stage_id`. Один источник нельзя использовать дважды. Старый экземпляр сохраняется целиком, новый разделяет линию награды и только оставшийся бюджет. Без mapping новые этапы начинаются с нуля; известные лексемы переносятся только по совпадающим ID. Завершённые старые результаты остаются в архиве, без новых знаний или медиа из предположений.

Семейный экран «Копии и перенос → Перенос в новую версию» поддерживает прежние задания и современные приключения с более новой ревизией. Он показывает уже выданный/оставшийся XP и отдельные списки сопоставления для новых этапов; перенос происходит после явного подтверждения. Общий статус старого задания не засчитывает новые действия.

## Файлы, полный backup и восстановление

`ArtifactService.import_local_image()` проверяет размер до декодирования: PNG/JPEG/WebP до 20 МиБ, сторона до 8192. `import_managed_file()` копирует архивы ZIP/PCK/TAR/GZ/TGZ/7Z до 200 МиБ без распаковки; связь версий — через artifact ID. Используйте управляемые имена и ссылки из версии работы, не абсолютный путь к семейному оригиналу.

| Полная семейная копия | Контракт |
| --- | --- |
| Экспорт | `BackupService.export_family_backup(state, destination, progress = Callable())`; destination — новая папка, существующая не заменяется; публикация папки через staging/rename |
| Формат | `manifest.json` (`sur_family_backup`, version 1), `snapshot.json`, `media/`, `launch_media/versions/` и `launch_media/working/` |
| Состав | Профиль и доступные управляемые файлы всех версий, сохранённые проекты/приложения и рабочая учебная папка |
| Исключения | Локальный `launch_registry/registry.json`, абсолютные пути/приватные launch-поля, `.tmp`, `.godot`; симлинки не принимаются |
| Пределы | Всего 2 ГиБ копируемых файлов, максимум 10 000 файлов, файл до 200 МиБ; каждый JSON метаданных до 16 МиБ |
| Проверка | SHA-256 снимка и каждого файла, допустимые имена/ссылки/размеры/схема до восстановления; отсутствовавшие оригиналы перечисляются в `missing_media` |
| Импорт | `import_family_backup(directory, progress = Callable())` → `{ok, state, media_count, launch_file_count, missing_media, launch_registration_required}`; копирует медиа, возвращает кандидат, сам профиль не записывает |

МиБ = 1024² байт; ГиБ = 1024³. Ограничение 2 ГиБ относится к файлам медиа/запуска; JSON ограничены отдельно. При коллизии различающиеся файлы получают новые имена, ссылки кандидата обновляются. `launch_entry_id` очищается: доверенный запуск требуется зарегистрировать заново. `source_archive_file` переносится только как проверенный относительный путь `launch_registry/versions/...` или `launch_registry/working/...`.

Для полного восстановления контроллер сначала показывает состав и спрашивает подтверждение, затем вызывает import и `Save.restore_snapshot(imported.state)`. Последний сохраняет текущие байты в отдельный `.before-restore-*.json`, проверяет и записывает поддерживаемый снимок, возвращает `{ok, state, preserved_file}`. Только явное восстановление может заменить профиль неизвестной схемы. Если запись не удалась, live-state остаётся прежним; уже скопированные медиа могут остаться отдельными файлами. Не называйте импорт файлов и запись профиля одной атомарной файловой транзакцией.

Локальное восстановление: `list_recovery_snapshots()` → выбор пользователя → `restore_from_backup(path)`. Эти JSON-снимки не содержат медиа. Экспорт пакета миссий и снимок расстановки также не заменяют полный backup. Семейная панель показывает сумму зарегистрированных материалов и пять крупных записей; это оценка, без отдельного объёма исходных ZIP и рабочей папки.

Необязательный callback `(phase: String, done: int, total: int) -> bool` вызывается на потоке операции; `false` возвращает `{ok:false, reason:"cancelled"}` после удаления своего staging/созданных копий, сохраняя существующие файлы. Счётчики относятся к текущей фазе; `total=0` — неизвестное число файлов при сканировании. Фазы экспорта: `export_prepare`, `export_media`, `export_scan`, `export_launch`, `export_metadata`, `export_commit`; импорта: `import_validate`, `import_media_validate`, `import_launch_validate`, `import_restore_launch`, `import_restore_media`, `import_ready`. Последние checkpoints стоят перед публикацией backup и выдачей кандидата. Проверки между файлами/фазами не прерывают уже начатый copy/hash одного файла.

`scripts/services/local_file_job.gd` запускает операцию в `Thread`, передаёт изолированное состояние и синхронизирует прогресс/отмену через `Mutex`. Callback не должен обращаться к Nodes. Контроллер опрашивает job и только на главном потоке после успеха и повторной проверки отмены вызывает Save. Не меняйте storage roots и не запускайте конкурирующие операции над теми же каталогами, пока job работает.

## Запуск учебной игры и настоящие исходники

`LaunchService.new(storage_root)` по умолчанию использует `user://launch_registry`. `prepare_starter_project()` читает проверенный ZIP из `assets/learning_starter/` через ZIPReader, создаёт редактируемую `working/station_light`, повторно использует помеченную копию без перезаписи. `register_project()`/`register_app()` сохраняют неизменяемые версии в `versions/<launch_id>/{project или Game.app, source.zip}` и локальные контрольные суммы; `launch()` проверяет их заново. Ограничения: 200 МиБ на версию, 4096 файлов, глубина 24, без симлинков. У `.app` поддерживается macOS-адаптер с XML Info.plist, не произвольный launcher или shell-команда.

Проект запускается через текущий редакторный бинарник Godot (`OS.create_process` с проверенным исполняемым файлом и фиксированными аргументами); в экспортированной SUR `register_project()` возвращает `godot_editor_required`. Обнаружение отдельно установленного редактора не реализовано. Приложение `.app` регистрируется отдельно. После переноса скопируйте восстановленную версию из managed `versions/` в отдельную рабочую папку и зарегистрируйте заново: прямой выбор из собственного хранилища версий запрещён.

**`source.zip` для зарегистрированной `.app` — архив бинарной сборки (`application_bundle`), не исходников.** `project_source` сохраняется при регистрации настоящего проекта. Для передачи авторской работы держите отдельно `project.godot`, сцены, `.gd` и ресурсы. Учебные `learning_projects/station_light/archives/station_light_<version>.zip` содержат настоящие проекты 0.1/0.2/0.3/0.4/1.0; `station_light_source.zip` — весь набор с инструментами. [README учебной игры](../learning_projects/station_light/README.md) описывает семь обязательных файлов и авторство подготовленной основы.

## Проверки без семейного профиля

Используйте общий проверенный запуск из корня репозитория:

```sh
python3 tools/run_checks.py --logs /tmp/sur-checks
python3 tools/run_checks.py test_adventure_app test_save_isolation --render --logs /tmp/sur-native-checks
python3 tests/test_isolated_session.py
python3 tools/run_checks.py test_developer_session test_developer_family --developer --render --logs /tmp/sur-dev-checks
```

`tools/isolated_session.py` создаёт свежую копию проекта и уникальный пользовательский каталог, устанавливает **`application/config/custom_user_dir_name`** и до запуска проверок сверяет фактический `OS.get_user_data_dir()` отдельным процессом Godot. HOME не меняется. После завершения или исключения созданные копии удаляются. `SUR_GODOT_BIN` позволяет выбрать редакторный бинарник. Runner ограничивает время процесса, сохраняет логи по указанному пути и после каждого набора сверяет SHA256 контрольного основного сохранения и всех резервных копий.

`Save.cleanup_test_storage()` только удаляет тестовые файлы и сохраняет выбранные пути. `restore_default_storage()` не снимает защиту тестового процесса: ни сохранение, ни reset/restore, ни загрузка/список резервных копий не могут перейти к стандартным семейным путям. Защита также действует при запуске через `--script`/`-s`; сравниваются нормализованные пути основного, временного и резервных файлов. Прямой запуск `test_save_isolation.gd` вне runner намеренно завершается с кодом 2, поскольку тест создаёт контрольные файлы именно на стандартных путях внутри временного user://.

### Ручная сессия разработчика

```sh
python3 tools/install_developer_launcher.py  # отдельная .app на рабочем столе macOS
python3 tools/launch_developer.py             # копия сохранения Майи, если доступна
python3 tools/launch_developer.py --mode family
python3 tools/launch_developer.py --mode prologue
python3 tools/launch_developer.py --mode adventures
```

Каждый запуск создаёт новые проект и user://. Только ручной launcher явно передаёт `family_profile_directory()` для чтения семейного файла: `capture_family_snapshot` копирует текущий `savegame.json`, `artifacts/` и `launch_registry/` в закрытый каталог временной сессии, а также фиксирует время снимка. Символические ссылки не переносятся. При изменении основного файла во время копирования снимок отклоняется; повреждённая/неподдерживаемая версия даёт объяснение в меню. Тестовый runner по умолчанию не читает настоящие семейные данные — нужные снимки создаются изолированными fixtures. Внутри работают обычные сохранения, вложения, редактор, публикация и реестр сборок. Закрытие удаляет сессию; следующий ручной запуск снова читает актуальное семейное сохранение. При доступном снимке ручной launcher стартует с него автоматически; без снимка предлагает пролог. `--mode family` явно требует семейный снимок. Режим помечен заголовком окна и кнопкой «ТЕСТ · прогресс до закрытия · меню F9». В меню **«Начать с сохранения Майи»** восстанавливает исходный снимок этого запуска, включая копии изображений, рабочих исходников и реестра. Перед этим останавливаются временные игры; оригинальные пути семьи не передаются игровому процессу. Также можно начать с пролога или подготовленных трёх миссий: последнее только пропускает пролог и публикует определения, не начисляя XP приключений. Самостоятельное включение режима без проверенного каталога и маркера останавливает приложение до загрузки профиля. Запущенные из сессии дочерние процессы завершаются при её закрытии. Это изоляция данных SUR, не системная песочница для произвольных внешних .app: внешнее приложение распоряжается своими файлами самостоятельно.

`test_adventure_infrastructure.gd` проверяет миграции/readonly/ошибки записи/пакеты/медиа/backup; `test_adventures_core.gd` — награды и перенос; `test_adventure_content.gd` — определения и адаптер запуска; `test_adventure_journeys.gd` — полные маршруты трёх историй и AR02. `test_adventure_scale.gd` создаёт 100 миссий, 30 экземпляров, 1000 работ с 3000 версиями, 20 комнат: лимиты открытия метаданных 500 мс, фильтра 200 мс. Печатает `SCALE_REPORT` с машиной, ОС, версией Godot, временем и замерами. Это проверка запросов без декодирования медиа и рендера, не измерение скорости UI.

`test_adventure_experience.gd` проверяет видимость реальных первых действий трёх историй при 100%/125%, все варианты первого ответа, объяснение ошибки, подсказку, настоящий `stage_attempt` после диалога, повтор записи при сбое, остановку/возвращение в выбранную сцену и открытие реальной наградной работы. С `-- --render` снимает нативные кадры в `/tmp/sur-experience-qa`. Автоматическая отправка ответа в диалоге не завершает этап и не обходит core: сцены всё равно проверяются сервисом; итог сохраняется отдельно. `work_requested(work_id)` ведёт через контроллер к конкретной работе. Повтор завершённого этапа остаётся локальной проверкой без команд начисления.

`test_adventure_authoring.gd` проходит кнопки настоящего редактора: ошибка записи → проверка без ложного закрытия, возврат из preview, добавление/удаление этапов, сохранение и выбор черновика, импорт → выбор → публикация → следующая ревизия, возврат после полного пересоздания AppRoot. Контроллер переносит `session_context()` редактора через изолированный preview; только подтверждённый ответ соответствующей команды разрешает закрытие или переключение формы.

Отдельная проверка упакованных учебных исходников сама работает во временной копии:

```sh
python3 learning_projects/station_light/tools/check.py --godot /opt/homebrew/bin/godot
```

Укажите свой путь к Godot. Опция `--screenshots` открывает окно и пишет изображения в `qa/`; для обычной проверки она не нужна. `tools/package_versions.py` заменяет подготовленные версии/ZIP — запускайте только при намеренной пересборке основы. Актуальные числа проверок и ручные результаты ведутся в [TEST_REPORT.md](TEST_REPORT.md).

`tests/test_learning_game.gd` нельзя запускать из корня SUR: он намеренно завершится с ошибкой и инструкцией. `check.py` переносит его в самостоятельные учебные проекты и проверяет каждую подготовленную версию.

## Аудит экспортируемой поставки

В [export_presets.cfg](../export_presets.cfg) есть preset `macOS`: все ресурсы, `include_filter="*.json,*.zip"`, исключение `tests/*`, `screenshots/*`, `docs/*`, `learning_projects/*`, `content/tools/*`. Он включает динамически читаемые JSON главы, словаря и AR02, а исходные ZIP основы берёт из `assets/learning_starter/`. Папка разработки учебного проекта в саму SUR не экспортируется. Preset настроен для локальной неподписанной поставки; для сборки нужны соответствующие export templates. Правила фильтров — в [документации экспорта Godot](https://docs.godotengine.org/en/stable/tutorials/export/exporting_projects.html).

Подготовка основы теперь использует ZIPReader, проверяет архив по manifest/SHA-256 и извлекает семь разрешённых исходных файлов. При следующих изменениях сохраняйте этот путь: `globalize_path(res://...)` не даёт обычный каталог исходников внутри экспортированного PCK — см. [ProjectSettings](https://docs.godotengine.org/en/stable/classes/class_projectsettings.html#class-projectsettings-method-globalize-path). Сцены/скрипты при экспорте также могут преобразовываться, см. [FileAccess](https://docs.godotengine.org/en/stable/classes/class_fileaccess.html).

Рекомендуется также передавать полный `learning_projects/station_light/archives/station_light_source.zip` отдельным файлом рядом с SUR: в нём инструкции, ступени и инструменты разработки. Не выдавайте архив `.app` за этот исходный ZIP. При пересборке учебной основы синхронизируйте ZIP и manifest в `assets/learning_starter/` с подготовленными версиями.

В текущей интеграционной проверке экспорт `/tmp/sur-final.pck` прошёл: подтверждены чтение JSON через FileAccess и извлечение учебной основы из ZIP внутри PCK. Экспорт PCK выполнен без установленных export templates. Это проверка упаковки ресурсов; готовая самостоятельная `.app` требует отдельной сборки и приёмки. Результаты фиксируются в [TEST_REPORT.md](TEST_REPORT.md).

Приёмка самостоятельной поставки должна запускаться без доступного checkout: читаются все три миссии и 100 лексем, импортируется AR02, создаётся полноценная рабочая копия с семью обязательными файлами, исходный ZIP открывается как проект, `.app` регистрируется и запускается, backup переносится без старого реестра доверия. Проверки из исходного дерева этого не доказывают.
